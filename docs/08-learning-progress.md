## 最近一课：代码定位与验证

这是对话中的模拟案例，尚未创建案例文件，未在仓库中发现或修复这个问题。

**症状：** 修改昵称后接口成功，列表仍显示 Alice，刷新页面后显示 Bob。

**候选解释：** H1 后端未保存；H2 前端缓存过期；H3 数据已更新但组件未更新。

**观察证据：** 首次 GET 返回 Alice；PATCH 返回 Bob；保存后没有新 GET；刷新后 GET 返回 Bob。这降低了 H1 的可能性，但单凭请求记录还不能确认 H2。

**定位过程：** 读取 `onRename`，发现它在更新成功后调用 `loadUsers` 并渲染；继续读取 `loadUsers`，发现存在缓存时直接返回旧列表。由此形成“服务端更新 → 再次读取命中旧缓存 → 渲染旧数据”的因果链。

**候选修复：** 更新成功后使相应列表缓存失效，再加载。此简化方案用于讲解，不声称处理了所有并发请求和缓存竞态。

**有效验证：** 先加载以建立 Alice 缓存 → 经过页面改名流程 → 不刷新页面 → 断言显示 Bob。只验证后端能读到 Bob，会绕开故障路径。

**证据变化：** 如果保存后已经 GET 且返回 Bob，调查应转向组件状态和渲染路径，不能继续凭原症状修改缓存。

分析每一步时使用四个问题：

1. 正在验证哪个假设？
2. 此次工具调用能排除什么？
3. 补丁是否对应已有证据支持的因果链？
4. 验证能否暴露错误补丁，且修复前能够复现失败？

“信息增益”是教学中分析动作价值的视角，不代表 Codex 源码显式实现了该公式。
