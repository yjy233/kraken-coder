# Kraken Coder 长任务运行验收

截至 2026-11-23，Kraken Coder 有一次**真实模型在约 10 分钟内自主修复故障并通过独立验收**的记录。同一题还有一次触达步数上限、未交付补丁的记录。小时级任务的完赛率仍待测量。[实验汇总](08-learning-progress.md)

## 什么算跑完

固定版本的仓库有一处故障。一条本机命令输出很长时，下一次模型请求可能超出上下文预算。模型拿到干净副本后，需要自行定位并修复。题面同时要求它新增回归测试，保住输出首尾、退出状态和磁盘日志原文。实验客户端通过正常的 Agent Server 接口提交题目和代答审批，评分器在候选仓库之外执行。[题面和运行入口](../eval/harness/run_shell_context.mjs)

| 检查 | 通过条件 |
|---|---|
| 回合终态 | 收到 `turn.completed`，无运行失败。单看助手最后一句“已完成”不足以判分。 |
| 外部行为 | 开始前在旧版重现 4 项失败，4 项短输出对照通过。修复后 8 项全过，覆盖两种算法、两种预算来源、长短输出。两种算法还需通过真实 shell 和 JSONL 的端到端检查。 |
| 补丁与回归 | 把模型新增的测试单独放回旧版能复现故障，在候选版通过。候选版原有测试、全量测试和类型检查通过。 |
| 改动范围 | 允许实现源码、新增回归测试，以及项目协作说明要求的 `docs/08-learning-progress.md`。其他额外路径使本次验收失败。 |

`summary.json` 的 `deliveryOK` 汇总终态、功能和回归检查，`pass` 是包括改动范围的最终判定。`baseline: 1` 是预期的旧版测试退出码。可以在运行目录的 `before.log` 找到具体失败断言。[行为检查](../eval/harness/check_shell_context.mjs) · [磁盘日志检查](../eval/harness/check_shell_journal.mjs)

## 两次真实模型运行

两次都用 `glm-5-3-flash-260828`、`learner` 模式、同一题面，从故障版本 `1fccb376` 的干净副本开始。运行 Agent 的版本为 `c21f9ac`。外部观察时限 15 分钟。客户端采用 `ask`，按固定规则批准补丁和题面内的测试命令，记录批准和拒绝次数。[实验配置](../eval/harness/run_shell_context.mjs)

| 指标 | 16 步上限（项目默认） | 48 步上限 |
|---|---:|---:|
| 模型实际步数 / 工具调用数 | 16 / 27 | 23 / 34 |
| 工具错误数 | 3 | 4 |
| 批准 / 拒绝 | 1 / 1 | 7 / 2 |
| 求解期间触发压缩 | 0 | 0 |
| 求解耗时 | 489.6 秒 | 595.1 秒 |
| 终态 / 最终验收 | `turn.failed` / 失败 | `turn.completed` / 通过 |

16 步那次，最后一份补丁的新增行格式无效。下一步报 `Step limit reached before executing tools`，候选目录没有改动，四个长输出用例仍失败。原有测试和类型检查本来就绿，这正是需要独立验收的原因。

48 步那次，候选补丁在 `src/context/budget.ts` 处理了 shell 的 `result.output`，并新增回归测试。8 项行为检查、2 项磁盘日志检查、108 项仓库测试和类型检查全部通过。补丁留在评测副本，实验没有把修复合入主程序。初版评分器把项目要求同步的学习记录判为越界，误判失败。保留初判后，只增加了这一条允许路径，离线重评两个原副本，结果见上表。本次整理又从主仓直接对两个候选运行外部检查，首轮行为检查通过 4/8、磁盘检查通过 0/2，第二轮分别通过 8/8 和 2/2，全程无需模型调用。这两个独立样本不足以推算把上限调到 48 后的成功率。[实验汇总](08-learning-progress.md)

## 怎么复跑、怎么复判

在仓库根目录使用 Node.js 24 或更高版本，首次运行先执行 `npm ci`。在根目录 `.env` 中配置待测模型。以下每条命令各发起一次真实模型任务，会消耗该模型的额度。运行器会在独立端口启动临时服务，终端打印本轮的 `eval/runs/shell-context-*` 目录。[运行说明](../eval/README.md#用当前模型验收一次多步任务)

```bash
node --import tsx eval/harness/run_shell_context.mjs --max-steps 16
node --import tsx eval/harness/run_shell_context.mjs --max-steps 48
```

复判已有实验时，把下面的目录名换成刚才打印的路径。它使用已保存的终态和候选代码，重新执行验收并更新 `summary.json` 及评分日志，过程无需模型密钥。先看 `pass`，失败时对照 `failure`、`after.log`、`journal.log` 和 `new-tests-before.log`。候选目录为 `project/`，原始模型轨迹在 `home/sessions/`。

```bash
node --import tsx eval/harness/run_shell_context.mjs --grade-run eval/runs/shell-context-实际目录名
```

本机保留的两次运行目录分别为 `eval/runs/shell-context-qlDT68/` 和 `eval/runs/shell-context-0ydpLA/`。后者含初判 `initial-grade.json`。这些产物被 Git 忽略，新检出项目需用上面的命令生成自己的副本。

## 离线压力与真实等待

另一次确定性压力测试给真实 Agent 循环接入脚本 Provider，按序读取 36 个约 5 KB 的文件，预算为 80,000 字符，最后用预计算标记核对文件内容和顺序。16 步时只完成 15 次读取，触发 2 次压缩，未收到最终答案。48 步时在第 37 次模型请求正常结束，36 次读取全部完成，触发 23 次压缩，36 个标记顺序全部匹配，耗时 1.155 秒。它验证重复压缩后循环能继续以及所选标记仍可见。上表的两次真实模型求解都没有触发压缩。[实验汇总](08-learning-progress.md)

磁盘日志专项检查同样使用脚本 Provider，但执行真实命令并读取实际 JSONL。一次候选复验中，发给模型的输出缩至 1,615 字符，落盘原文保留 13,584 字符，退出码仍是 9。此项已纳入常规复判。36 文件压力脚本目前只在本机留存，有产物时可在仓库根目录运行 `node --import tsx eval/runs/long-loop-offline-HdR2Vh/probe.mjs`。[磁盘日志检查](../eval/harness/check_shell_journal.mjs)

另一次离线重启实验在等审批时直接从磁盘读到 22 条完整 JSONL 记录。正常停止服务后，用同一数据目录启动新进程，原轮次显示已取消。同一 session 再发起一轮并完成，日志增至 37 条，前 22 条逐条一致。这验证了执行中落盘和跨进程续聊。服务被强制杀死后自动接着执行未完成的工具，仍是另一项待验能力。[会话落盘实测记录](08-learning-progress.md#当前断点与下一次入口)

本机还有一轮真实会话，从开始到取消共 **37 分 11 秒**。按 JSONL 中审批请求到答复或回合结束的区间统计，约 **35 分 51 秒**处于等待审批状态，最后也没有交付。统计长任务时要分别报告墙钟耗时、等待审批时长和终态。两者的差值还包括网络、模型和工具等待，不能当作模型思考时长。

## 下一次怎样验收小时级任务

1. 选一个实际需要跨阶段工作的真实任务，例如把旧版会话迁移到新版，并同时验收旧记录恢复、新记录写入和中断恢复。先锁定基线和题面，把独立验收放在候选仓库外，确认旧版确实失败。预先写下成功条件，避免看到补丁后改题。
2. 为该题设置能覆盖目标时长的运行器观察时限和整轮时限，记录模型、步数上限、版本和审批策略。现有故障脚本在 15 分钟时主动中止，即使服务的整轮时限配为 3 小时，仍需为小时级实验调整外部时限。期间按固定规则代答审批，并记录每段等待。
3. 从干净副本独立跑多次，报告“通过次数 / 尝试次数”。保留失败、取消及超时的样本。每轮列出终态、交付物验收、总时长、扣除审批等待后的时长、模型步数、工具错误和压缩次数。
4. 只有样本实际覆盖目标时长、有持续的任务进展且外部验收通过，才把它计为一次小时级完赛。提前交付的样本照实记录为对应时长的成功。当前已验证的最高结论仍是本题约 10 分钟的多步交付。
